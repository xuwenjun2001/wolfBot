## 一、自评说明

本人围绕 wolfbot 项目开展 AI 系统化应用实践，将大模型、业务数据、工具调用、知识与记忆接入、任务编排、质量评测和交互界面组合成可运行的研究系统。应用覆盖自然语言数据分析、财报变化研究、证据核验和报告修订，形成从需求输入到结果交付、再到评测改进的完整流程。

本项目体现的能力包括：将业务问题拆解为 Agent 可执行任务；为模型配置专业工具和 Skills；将模型输出与真实数据、确定性计算和原文证据结合；通过版本管理、权限隔离、预算控制和故障恢复保障执行；根据实验结果决定是否采用优化方案。因此，本人按“能够构建、应用和持续改进 Agent 系统”的能力维度自评为 L4，最终等级以评审标准为准。

本材料中的优化主要指 Agent 工作流程、提示词、Skills、工具和评测体系的改进，不涉及基础大模型预训练或参数微调。项目基于开源 PI Agent 内核建设应用与治理能力，相关成果不表述为自研大模型或从零开发底层 Agent 框架。

## 二、案例一：基于原始财报的变化研究 Agent

### 业务问题

对比一家公司的两期财报，通常需要反复查找收入、利润、现金流及风险说明，再核对期间、单位和原文依据。直接让大模型总结，容易出现数字抄错、引用无法定位，或将指标相关性解释为因果关系的问题。

### 实现方式

围绕这一场景，项目建立了“提出研究问题—生成计划—获取和解析资料—检索证据—计算变化—核验结论—生成报告”的 Agent 流程：

1. **明确研究范围。** 将公司、两期报告、资料截止日和研究问题保存为结构化请求，生成可查看、可修改的研究计划。
2. **读取真实资料。** 接入原生 PDF 解析与独立 OCR 服务，保存原件版本和内容指纹；检索按用户、公司、期间与资料截止日约束，避免混入不属于本次研究的资料。
3. **让模型与程序各司其职。** 模型负责理解问题、选择工具和组织解释；金额单位转换、差额及增幅由十进制计算程序完成，保留原始数值和出处。
4. **分层核验。** 分别检查引用是否存在、数值是否来自正确的期间列，以及原文是否支持结论。缺少原因依据时保留缺口，不强行补全解释。
5. **交付可复核报告。** 用户可从结论跳转原文、查看页码和高亮，修改研究问题，并比较不同版本报告的变化。旧版报告保持可读。

### 代表性成果与效果

项目已形成财报变化研究工作台、原文阅读器、计划修订和报告版本差异功能。已有认证浏览器旅程验证报告读取、原文定位、修订提交、刷新恢复与取消；演示使用真实模型报告存档重放，不代表演示现场重新调用模型。

在冻结的四家公司开发集上，修复数值校验器后运行的基线结果如下。以下数字引用已有实验记录，本次材料整理没有重新运行模型。

| 评价项 | 实验结果 | 统计口径 |
| --- | --- | --- |
| 必需数值正确项 | 36/36，100% | 两期金额及增幅，缺答计错 |
| 完成研究问题 | 11/12，91.67% | 必要数字正确且相关结论受支持 |
| 实质结论支持 | 11/12，91.67% | 经有限校准的同模型独立调用审查 |
| 整公司任务完整完成 | 3/4 | 另 1 家保留部分完成状态 |

上述结果来自四家公司、每家公司一次运行，不能外推为全市场准确率。保留集已有两次任务结果，但独立人工参考尚未核查，因此不报告保留集准确率。

这一案例的直接应用价值是：把资料查找、数值比较、解释生成和人工复核组织到同一个工作流，使研究结论有据可查，缺失信息可以被看见。项目尚未开展人工耗时对照，不填报未经测量的提效比例。

## 三、案例二：自然语言驱动的数据分析工作台

### 业务问题

金融分析需求经常同时涉及证券识别、行情获取、指标计算和图表展示。传统方式需要在多个工具之间搬运数据，也需要开发人员反复搭建类似页面。

### 实现方式

项目将自然语言需求转化为结构化任务计划，再通过金融领域能力和 Skills 生成独立的 Next.js 数据工作空间。例如，用户可提出比较某只股票在指定期间的价格与成交量等需求，由系统完成语义理解、证券身份核验、数据预取和页面生成。

这条链路的关键是把业务约束写入可执行流程：模型生成结构化语义合同，证券解析器复核标的；数据文件与来源证据分别保存；生成后检查构建、HTTP 预览、数据契约和视觉展示；失败时生成修复清单，驱动 Agent 在当前工作空间修复并再次验证。模型规划失败时停止下游处理，避免用猜测结果继续交付。

### 成果与应用价值

产物包括可构建和预览的页面源码、结构化数据文件、数据来源、质量说明及验证记录。用户得到的是能够继续使用和修改的数据工作空间，研究者也能够追溯数据口径和缺失项。

平台将通用 Agent 执行能力与金融规则分层，后续扩展其他业务领域有明确接入边界。目前主要落地领域仍是金融，不能据此宣称已完成零售、制造等多行业应用。

**核验材料：** [工作空间生成链路](learning/02-ai-workspace-generation.md)、[生成工作空间契约](generated-workspace-contract.md)、[Data Agent 架构](data-agent-architecture.md)。本案例说明已有系统机制，不填报尚未核实的用户规模、交付成功率或商业收益。

## 四、案例三：用评测和运行治理持续改进 Agent

### 实践问题

Agent 能够生成一次正确答案，并不意味着它可以持续可靠地运行。提示词变长或工具调用变少，也不一定代表整体效果变好。项目因此同时建设质量实验和运行治理能力。

### 评测驱动的优化过程

项目固定开发资料、模型、评分规则和单任务预算，对原版研究 Skill 与一个候选提示词开展配对实验。参考答案不提供给生成器；实验保存失败、部分完成、工具调用与 Token 用量，选择方案后才开启保留验收。

| 对比项 | 原版基线 | 候选方案 |
| --- | --- | --- |
| 必需数值正确项 | 36/36 | 36/36 |
| 完成问题与实质结论支持 | 均为 11/12 | 均为 9/12 |
| 整公司完整完成 | 3/4 | 2/4 |
| 工具调用总数 | 146 次 | 127 次 |

候选减少了 19 次工具调用，但问题完成和结论支持均回退，未达到质量门槛。最终保留原版，没有将候选发布为默认方案。这项实践体现了基于证据判断优化效果的能力，也说明“拒绝一次质量退化的优化”是质量管理的实际成果。

另一次真实失败暴露了财报行内金额单位识别不足。项目保留原失败记录，修复校验器并回放 47 条原表失败输入，再重新登记实验。该修复属于校验组件改进，不将修复前后两个批次的差异包装为 Skill 提升。

### 运行治理与成果

研究任务具备独立 Worker、租约和执行代次校验，进程中断后可接管任务，并拒绝失效执行者写入；修订与接管沿用原逻辑任务预算，不能靠重启获得新预算。平台同时保留任务状态、工具调用、成本用量和公开检查点，便于排查失败。

既有验收记录包含 44 项隔离 PostgreSQL 测试，以及一次真实子进程中断与接管实验。这些证据支持恢复机制的工程验证，不等同于经历 44 次生产故障。

**核验材料：** [配对实验与方案取舍](plans/research-agent-upgrade/evaluation-results.md)、[可靠性与恢复](plans/research-agent-upgrade/reliability.md)、[当前验收与交接记录](plans/research-agent-upgrade/progress.md)。

## 五、与 L4 系统化应用能力的对应关系

| 能力维度 | 本项目中的具体实践 |
| --- | --- |
| 业务问题建模 | 将财报研究拆为期间、问题、计划、证据和交付要求 |
| Agent 设计与应用 | 组合模型、Skills、专业工具和多轮执行流程，形成可运行产品 |
| 数据与知识接入 | 接入行情、财报、知识与可选记忆服务，保留来源和作用域 |
| 可靠输出 | 用确定性计算、原文引用和结论核验约束模型输出 |
| 人机协作 | 用户可查看和修订计划、定位原文、复核报告；机器完成与人工验收分开 |
| 持续优化 | 依据冻结评测、失败轨迹和配对实验决定修复或保留方案 |
| 工程化交付 | 建设权限、任务持久化、预算、故障恢复、版本管理和验证机制 |

本人的自评依据是上述系统化应用实践，而非单次提示词使用或内容生成。项目已形成代码、交互工作台、实验记录和可核对文档，能够展示从业务需求分析到 Agent 应用交付及质量改进的完整思路。
