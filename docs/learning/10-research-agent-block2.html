01 · 先认识问题

板块 2 做的是“研究过程的工程化”

读完这课，你应能用两分钟说明：这五个工作包解决什么问题，哪些收益已经验证，哪些还要实验。

设想你让 Agent 比较一家公司的两期年报，回答三件事：收入和归母净利润怎样变化，经营现金流为何变化，风险提示有什么变化。它可能连续搜索现金流原因，反复读相同页，直到第 40 次才发现还有结论没核验。此时“再认真一些”的提示词无法补回工具额度。

我们把这类要求从文字建议拆成应用代码：当前可以研究哪一问、允许调用什么工具、有没有新增证据、再搜多久应该停止、接下来还够不够核验和交付。模型仍负责理解与选择，代码负责约束每一步。

A、B、B2 与以后多 Agent 的关系

A 是原有行为，也是新任务省略选项时的默认值。B 是原单 Agent 加调度，仍然每轮一个工具。B2 继续使用 B 的计划和预算，一轮可输出多个工具。C1 / C2 才是后续三研究员串行 / 并发方案，当前没有在这五步中实现。

B/B2 通过可信调用方给 executeFinancialResearch(..., options) 注入。它们不会因代码落地就自动切换日常 Worker；消融 CLI 的真实 adapter 仍待接入。学习时要区分“运行时能力已实现”和“实验入口已获准执行”。

先补几个名词：节点、claim、locator、hash、checkpoint、fencing

节点是一个有依赖和完成条件的工作阶段。claim 是待核验的结论。locator 指向 PDF 页、表格单元或文本块。hash 是材料内容的指纹。checkpoint 是恢复所需的公开状态。fencing 是服务端拒绝旧 Worker 写入的执行权校验。它们都不是模型的隐藏思维链。

03 · U10 计划图

从“有一个清单”到“知道现在能做哪一步”

学会读依赖图，解释为何风险研究不必等财务金额齐全，以及为何只修一条分支。

DAG 是有向无环图：箭头表示必须先完成的依赖，图中不允许绕一圈回到自己。新计划有一个共享 prepare-facts 节点，加上三问各自的 retrieve → compare → verify → report，合计 13 个节点。旧 v1 的 12 步列表仍作为兼容投影保留，真正的执行权限来自 v2 节点。

共享准备只要求做一次有界准备，不要求六个金额全部成功保存。收入利润与现金流依赖准备；风险分支不依赖准备。调度器可以让 partial 阶段把诚实的缺口交给下游，它不会把公开的 partial 标签改成 completed。纯 readyNodes 只接受 completed 依赖，运行时通过 effectiveStates 做这层投影。

04 · U11 缺口策略

“还没找到”也必须有结构和停止条件

“现金流原因暂时没找到”不能只是上下文里的一句话。我们把它存成缺口，绑定目标节点、问题、对象、已见定位和内容指纹，并累计尝试次数。这样换关键词、压缩上下文或 Worker 接管都不会让历史消失。

缺口含义与修复方向
retrieval_miss还缺目标证据：有 locator 时定向读，否则搜索
not_disclosed有覆盖指定两期的可信未披露回执；不是搜索失败的同义词
period_unit_conflict期间、单位或原值冲突：回看表头/单位/原文，不能硬合并
tool_transient工具临时失败：有界重试；不可重试的失败直接保留缺口
unverified_claim结论尚未核验：转向指定 claim 的核验
budget_exhausted预算不足：停止扩展，按余额核验或收尾

判断进展看新增 locator 或证据内容 hash。同一页里读到新的文本块可以增加信息；只是换搜索词、改页码显示标签、反复交回相同文字，都不能作为新增证据。检索缺口连续 4 次无增量停止，累计最多 8 次；其他需修复类型通常最多 3 次，预算与截止时间还能让它更早停止。

    05 · U12 预算策略

    先留出核验与交付的额度，再决定能不能继续研究

    预算总额仍由父任务管理，默认 40 次工具和 20 分钟。策略只做分配建议与准入判断；真正的扣额仍由 reserveResearchToolCall 在服务端原子完成。每个节点不会额外得到 40 次，也不能通过重规划、恢复或改写结论把用过的额度清零。

    收尾预留 = 当前还需核验的 supported 草稿数量 + 2“+2”分别留给 check_coverage 与 submit_report。计数按逐条 claim 的当前内容/证据 hash 是否已有核验回执，不按三问各算一次。显式 evidence_gap / conflict / incomparable 已保留诚实缺口，不再按 supported 草稿重复预留。核验回执存在也不等于核验获支持，失败仍按缺口处理。

    当余额进入预留区，allowedNow 只允许核验、覆盖检查与提交；其余工作转 partial。它只是第一道检查，最终还要符合节点白名单、claim 绑定和执行权。余额为 0 时所有工具都不能继续。

    此处计算预留和单条新增结论的简化准入；没有模拟完整节点、时间与 SQL 事务。图中“已耗用”假设总额为默认 40。

    为什么还要检查“写入之后”的预算？

    假设没有待核验草稿，余额 3、预留 2。只看调用前，record_claim 可以花 1 次；但若新增 supported 草稿，调用后余额只剩 2，新的预留却变成 3，最后无法提交。修复后先投影真实的事实合并/结论更新，再计算新 hash 和新预留。若 remaining - 1 < reserveAfterWrite，拒绝发生在保存和扣额之前。事实修改使旧核验失效时，同样适用。

    节点软份额怎样避免一个问题吃光额度？

    初始权重为准备 10%，每个问题的检索 15%、比较 5%、核验 7%、报告 3%，总和 100%。它们用于调整工作优先级，采用稳定的整数分配；阶段结束后未用份额可以让给其他节点，已经消耗的调用不会返还。软份额不是“到第 6 次就强制停搜”的硬阈值；必需事实还没保存时，不能只因达到份额就截断本问。

    把规则装进真实循环，才形成变体 B

    前三步都是能单独测试的纯策略。U13 新增 FinancialScheduler，在真实研究运行时里给模型提供 nextAction，然后逐项决定它提出的调用能不能执行。模型能看见目标节点、问题、允许工具和修复建议，但工具请求还要接受代码检查。

    1. 从公开状态计算 nextAction

      刷新当前核验义务和节点状态，判断依赖与缺口；优先给三问检索/比较机会，再进入更深修复与报告。风险独立就绪，不代表它一定先于准备运行。

    2. admit 检查当前工具

      检查预算预留、节点白名单、问题归属、指定 claim、写入后的预留。不能复用别题 claim ID 覆盖它的结论。

    3. 通过后原子扣额，再执行

      服务端检查租约/版本并预留本次工具次数。通过准入才产生实际调用；工具自身的原文、期间、权限与 schema 校验继续保留。

    4. 观察结果，决定进展或修复

      新增证据更新 ledger；空结果累计停滞；冲突保留冲突；核验失败只在缺口仍 open 且余额充足时局部重规划。

    5. 保存 checkpoint 与事件

      局部修订的状态和 plan.revised 在同一受执行权约束的事务里保存。下一轮或接管从这份公开状态继续。

    写了一条 claim，为什么还不能马上离开比较阶段？

    一问可能需要多个事实、多条结论。当前实现让 record_fact / record_claim 只做逐条保存，最后调用 complete_comparison({questionId})。收入利润需要两期收入和归母净利润，现金流需要两期经营现金流；还要有本问结论。材料不足时必须明确保留缺口，否则完成请求被拒。

    complete_comparison 只是结束本问比较，不能代替核验、覆盖检查或报告提交。正常完成三问会额外消耗三个父预算内工具次数；预算已进入预留区时，可以由调度器把尚未完成比较标为 partial，给核验和提交留下空间。

    把一次调用拆成“政策”和“事实”两层策略判断“这项行动现在合适吗”；工具验证“这项原文和数值真的成立吗”。预先投影材料不能冒充原文验证，实际写入仍需通过现有证据和权限检查。

    07 · U14 批量工具

    一轮提出多个请求，仍然逐个顺序执行

    B2 默认允许一轮最多 3 个工具，上限可配置为整数 1—8。Provider 只在 B2 开启多工具输出；PI 继续使用顺序执行模式。模型少往返几次是可能收益，工具并没有同时开跑。

    第一层：整轮预检查

    先检查数量、唯一 ID、工具是否注册、所有参数 schema、整批余额和预留，再在复制的公开状态上检查已知节点约束。后项已经确定无效时，首项也不应该执行或扣额。

    第二层：每项重新准入

    前项的结果可能改变节点、余额或执行权。轮到每一项时重新检查，然后独立原子扣额。后项不再允许就只拒绝后项，不回滚先前的真实消耗。

    一轮最多一个状态工具，且必须排在只读工具之后。状态工具包括 record_fact、record_claim、complete_comparison、verify_claim、check_coverage、submit_report，也保守包含 import_filing / parse_document。submit_report 必须独占一轮，不能“搜索完顺手提交”。

      预设参数是合成的；演示“批次检查 → 单项准入 → 扣额”的关系，没有在浏览器执行生产工具。整轮工具拒绝也仍然发生过模型请求，不能称为零成本。

      “测试通过”之后，为什么还修了三项？

      首轮 U14 有 231 单测和 64 PG 测试通过，之后 review 仍找出三条没有覆盖的执行轨迹。这里保留这段过程，因为理解缺陷比背诵“用了 DAG 和预算”更能帮助你掌握设计。

      发现触发与影响修复后的行为
      R1 · partial 更新重试卡住submitted 已清，但 report 节点仍终态，即使还有 28 次余额也可能 nextAction=null重开 report 节点；保留停止的研究、缺口、证据、计数与未读来源
      R2 · 第一条结论过早结束 comparerecord_claim 后离开比较，后续必需金额或第二条结论没机会保存逐条保存，complete_comparison 显式结束；缺必需材料时不冒充完成
      R3 · 只看写入前预留余额 3/预留 2 时花 1 次新增 supported 草稿，却新增 1 次核验义务，不能提交投影写后事实/结论及 hash，按写后预留拒绝；B2 整批和逐项都检查

      R2 同时说明“保存操作成功”和“阶段完成”应分开建模。R3 说明预算不是一个静态计数器：一次写入会增加后续必须承担的工作。R1 则说明恢复不是只清一两个布尔值，而要把所有能阻塞下一动作的终态一起考虑。

      新增测试补的是执行轨迹，原有门槛继续保留修复后工程记录为 246 单测、71 PG 通过。首轮新增 PG 夹具曾把上一期金额引用到本期报表而失败，修正的是合成夹具中的期间引用，期间校验没有放松。原 review 复现、失败日志与后续通过记录分别保存。

      旧 checkpoint 可能带有“比较过早完成”的状态，覆盖检查在预算允许时局部重开这个 compare；已停止缺口不重开，无关问题的核验也不作废。兼容不是把旧状态直接当成新版本已经正确执行过。

      10 · 串成一次研究

      从用户问题到报告，五个工作包怎样协作？

      用一家公司两期已导入年报作为教学前提，不提供真实数值和标准答案。目标仍然是收入利润、现金流和风险三问。下面是可能的执行片段，不是固定工具顺序，也不承诺一定完整完成。

      1. 从任务和资料构造图 · U10

        加载 asOf、两个期间和来源版本，建立共享准备与三条研究链；风险不受金额准备的全局门槛阻塞。

      2. 模型读到原文，及时保存材料 · U13

        search 找定位，read 核对表头与单位，record_fact 保存逐字原值。比较阶段把本问多条结论都存好，再 complete_comparison。金额变化仍用确定性计算。

      3. 现金流原因找不到 · U11

        建立 retrieval_miss，按 locator 定向补查。如果不断换词却没有新增证据，计数不会清零；达到停止条件就保留缺口，而不是编造“需求恶化”或“未披露”。

      4. 余额接近核验预留 · U12

        调度器停止扩展检索，把未完成的研究标 partial；在剩余额度内逐条核验当前 claim。新写入若会产生付不起的核验义务，提前拒绝。

      5. 把独立只读请求合在一轮 · U14

        例如同一节点对两期原文的两次定向读取。整批参数先检查，PI 逐个执行，观察到节点变化或取消后不预扣后项。不能把两次 record_fact 放在一轮。

      6. 提交可追溯报告 · 既有报告能力 + U13

        check_coverage 检查材料与差异，submit_report 单独一轮提交。最终发布继续核对执行权、版本、来源和核验回执。报告保留缺口、变体和可用的模型轮数。

      这里的 Agent 能力在哪里？

      它不是照顺序播放一个固定脚本。工具结果会改变缺口、下一动作、修复位置和可用预算，模型在这些约束下继续决定怎么找证据。计划图提供结构，节点内仍由观察驱动行动；批量调用只改变每轮承载多少请求，不自动增加独立研究员。

      你可以把 B 概括为“有执行约束的单 Agent 研究循环”，把 B2 概括为“相同调度规则下减少模型往返的多工具输出变体”。是否提高质量和省钱，仍须用同样资料、模型、评分与总预算做配对实验。
